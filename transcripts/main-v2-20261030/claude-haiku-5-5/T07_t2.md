## Reply

**Key rules applied**

- **Matching:** `value-quantity` matches only Quantity values. `w-10` (`valueString`) is never returned. The `system|code` parts must match, and no unit conversion is done, so `w-05` (lb, `[lb_av]`) never matches a kg query.
- **Implicit ranges (eq/ne):** The search value `100` covers [99.5, 100.5). The search value `100.0` covers [99.95, 100.05). Upper bounds are exclusive.
- **Exact comparison (gt/lt):** Prefixes compare the stored point value directly, ignoring the search value's precision.
- **w-08:** It has a unit but no `code`, so it can't match a query that specifies `kg` as the code. This is the only edge case where I'm applying the rule strictly. A server that matched on `unit` would return it for q1 and q3.
- **w-09:** Its unit text is "kilograms", but its `code` is `kg`, so it matches on code.

**Per query**

- **q1** `100|UCUM|kg` (range [99.5, 100.5)): w-01 (100), w-02 (100.4), w-04 (99.5, inclusive lower bound), w-06 (100.04), w-07 (99.94), w-09 (100.0). Excluded: w-03 (100.5, outside the exclusive upper bound), w-08 (no code), w-05 (lb).
- **q2** `100.0|UCUM|kg` (range [99.95, 100.05)): w-01, w-06 (100.04), w-09. Excluded: w-07 (99.94 is below 99.95), w-02, w-04, w-03.
- **q3** `100||kg` (no system, so any system with code `kg`; range [99.5, 100.5)): same as q1, because w-08 has no code and w-05 has code `[lb_av]`.
- **q4** `gt100|UCUM|kg` (value > 100, exact): w-02 (100.4), w-03 (100.5), w-06 (100.04). w-01 and w-09 equal 100, so they are excluded.
- **q5** `ne100|UCUM|kg` (not in [99.5, 100.5)): only w-03 (100.5) lies outside the range. w-01, w-02, w-04, w-06, w-07 and w-09 are all in the range. w-08 has no code, and w-05 has a different unit code.
- **q6** `lt100.0||kg` (value < 100.0, exact, no system): w-04 (99.5) and w-07 (99.94). w-05 is excluded because its code is `[lb_av]`, not `kg`, and no unit conversion is applied.
