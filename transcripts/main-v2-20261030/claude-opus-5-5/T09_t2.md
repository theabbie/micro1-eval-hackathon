# FHIR R4 Search Results for Task T09

## Key rules applied

- **Separate parameters are not correlated.** In q1, `component-code` and `component-value-quantity` are evaluated independently. Each can be satisfied by a different component of the same Observation.
- **Composite parameters are correlated.** `component-code-value-quantity` requires the code and the value to match within the same component.
- **Missing values never match.** The bp-06 diastolic component has `dataAbsentReason` instead of a value, so it cannot match any quantity criterion.
- **Prefix comparisons are exact.** `ge`, `gt`, `le` and `lt` ignore the search value's precision.
- **No prefix means `eq`, which uses an implicit range.** That range comes from the digits written: `140` covers [139.5, 140.5).
- **No unit checking.** The search values carry no units, so any unit matches.

## Per query

**q1:** `component-code=…|8462-4` matches every panel that has a diastolic component, which is bp-01 through bp-09. This includes bp-06, because its component still has the code even without a value.
- `component-value-quantity=ge90` matches if any component is ≥ 90.
- Every panel has a systolic value ≥ 90, so every panel passes.
- The query never links "diastolic" to "≥ 90". This is the classic false-positive trap.
- Result: bp-01 through bp-09.

**q2:** The diastolic component must itself be ≥ 90.
- Matches: bp-02 (95), bp-04 (92), bp-07 (90) and bp-08 (91).
- bp-09 (89.6) fails because the comparison is exact.
- bp-06 fails because it has no diastolic value.

**q3:** The comma makes this an OR: systolic ≥ 140, or diastolic ≥ 90.
- Systolic ≥ 140: bp-01, bp-04, bp-06, bp-07.
- Diastolic ≥ 90: bp-02, bp-04, bp-07, bp-08.
- The union is then ANDed with `status=final`, which removes bp-08 (entered-in-error).
- sbp-01 has no components, so it cannot match.
- Result: bp-01, bp-02, bp-04, bp-06, bp-07.

**q4:** The repeated parameter makes this an AND: systolic ≥ 140 and diastolic ≥ 90.
- Result: bp-04 and bp-07.

**q5:** Systolic `eq 140` uses the range [139.5, 140.5).
- bp-07 (140) matches.
- bp-09 (139.6) also matches, because it falls inside the range.

**q6:** `code-value-quantity` looks at `Observation.code` and `Observation.valueQuantity`, not at components.
- Only the standalone sbp-01 (152) matches.

**q7:** Matches any Observation whose top-level `valueQuantity` is > 90, regardless of unit.
- hr-01 (98 /min) matches, even though it is a heart rate.
- sbp-01 (152) matches.
- The panels have no top-level value, so they cannot match.

## Registry implications

- **q1 is unsafe.** It flags every panel. Use the composite form (q3) instead.
- **q7 pulls in heart rate.** Add a `code` filter, or add units to the quantity search, for example `gt90|http://unitsofmeasure.org|mm[Hg]`.
- **q3 misses the standalone systolic Observation.** sbp-01 (152) is above goal but is not returned. You need an additional query such as q6 to catch it.
- **bp-09 decimals:** the 139.6/89.6 reading is excluded by `ge`. Decide whether your registry wants rounding behaviour here.
