# T11 Results: Reverse Chaining, Chaining and Includes

## Shared facts

**HbA1c Observations** (code `http://loinc.org|4548-4`):

| Observation | Value | Subject | Status |
|---|---|---|---|
| o-1 | 9.5 | pt-1 | final |
| o-3 | 7.0 | pt-2 | final |
| o-5 | 9.2 | pt-3 | final |
| o-6 | 10.1 | pt-5 | entered-in-error |
| o-8 | 11.0 | pt-9 | final (pt-9 is not on the server) |

**Value-quantity > 9 with any code and no unit conversion:** o-1, o-2, o-4, o-5, o-6, o-7, o-8, o-9. Only o-3 (7.0) fails.

## q1: two separate `_has` parameters

Each `_has` parameter is evaluated on its own. One Observation can satisfy the code criterion and a different Observation can satisfy the value criterion.

- Patients with any HbA1c Observation: pt-1, pt-2, pt-3, pt-5. pt-9 is not on the server.
- Patients with any Observation where value > 9: pt-1, pt-2 (o-4 = 250 mg/dL), pt-3, pt-4, pt-5.
- The intersection is pt-1, pt-2, pt-3 and pt-5.

pt-2 is a false positive. Its HbA1c is 7.0, and it matches only because its glucose (o-4) is 250.

## q2: composite `code-value-quantity`

A composite parameter requires code and value to match on the same Observation. The matching Observations are o-1, o-5 and o-6, so the result is pt-1, pt-3 and pt-5. Status is not filtered, so the entered-in-error o-6 still counts.

## q3: q2 plus a separate `_has` on `status=final`

The status criterion is independent of the composite criterion.

- pt-1 has final o-1.
- pt-3 has final o-5.
- pt-5 matches through o-7, which is a final glucose result.

The result is pt-1, pt-3 and pt-5. pt-5 is still a false positive. Its only qualifying HbA1c is entered-in-error.

## q4: composite plus chained `patient.gender=female`

- The composite matches o-1, o-5, o-6 and o-8.
- o-1 (pt-1) and o-5 (pt-3) have female patients.
- o-6 (pt-5) has a male patient.
- o-8 references pt-9, which does not exist here, so the chain cannot resolve.

The result is o-1 and o-5.

## q5: composite plus `_include=Observation:patient`

- **Match:** o-1, o-5, o-6, o-8.
- **Include:** pt-1, pt-3, pt-5. pt-9 cannot be included because it is not on the server.

## q6: `patient=pt-2` plus `_revinclude=Provenance:target`

- **Match:** o-3, o-4.
- **Include:** prov-2, which targets both o-3 and o-4.

## q7: `_has` HbA1c, `gender=female`, and two revincludes

- **Match:**
  - Patients with an HbA1c: pt-1, pt-2, pt-3, pt-5.
  - Female patients among them: pt-1, pt-3.
- **Includes:**
  - `Provenance:target` adds prov-3, which targets pt-1.
  - `Observation:patient` adds all Observations for pt-1 and pt-3, not just HbA1c: o-1, o-2 and o-5.

## Integration takeaways

- Use the composite parameter rather than separate `_has` parameters. Separate parameters let the code and value come from different Observations (pt-2 in q1).
- Add `status` inside the same `_has` chain where possible, or post-filter. A separate `_has:...:status` does not exclude entered-in-error results (pt-5 in q3).
